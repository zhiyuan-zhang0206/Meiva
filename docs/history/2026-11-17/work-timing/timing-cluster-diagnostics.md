# Timing diagnostics belong in cluster events

The user's 20:59:50 ruling replaces the earlier visible-warning decision: missing work timing shows plain "Worked" ("Working…" while active), without a warning icon, tooltip or accessible warning. Complete measurements, including zero, retain their duration. A partial subtotal stays internal.

Missing or null native durations are expected unknown data. A present invalid duration on a completed planner is a collection failure. Existing anomaly events carry collection failures, corrupt sidecars, ambiguous identities and unavailable records. Native content and exception text stay out of these diagnostics. Sidecar corruption still warns when historical records have no active collector.

Invalid duration step indices join the collector's native-facts digest. The existing unchanged snapshot and record watermark fast path suppresses repeated diagnostics after a successful sidecar write. Changed facts or record bytes may diagnose again; a failed write retains the existing repeated failure behavior. Historical sidecar parse diagnostics retain the existing reader-instance revision gate. Reconstructing a reader may report that real parse failure again. No process-global cache or logging infrastructure change is introduced.

Reuse the existing cluster warning aggregation. At base 3b9e2fe315, `deploy/lgtm/config/grafana/provisioning/alerting/rules.yml` declares `meiva-ops-warning-error-spike`: one-minute evaluation, five-minute current count C, previous fifteen-minute count D offset by five minutes, predicate `C > D && C >= 30`, sustained for five minutes. Because D covers three five-minute windows, this compares against three times the prior per-five-minute average. Low volume and steady non-spiking warnings remain searchable without firing this rule. Its recovery window is five minutes.

The source chain is loguru's `base/telemetry/process_logging.py` adapter, the unified emitter and delivery drain, PostgreSQL `telemetry_events` (`event_store.is_persisted` retains warning and higher), and the OTLP log exporter to Loki. The rule filters `.meiva`, telemetry/log categories and warning/error/critical levels. Timing events already belong to those categories and require no new rule or metric labels. Source configuration establishes intended coverage; production installation and delivery require operator verification by Meiva #405 / #1818.
